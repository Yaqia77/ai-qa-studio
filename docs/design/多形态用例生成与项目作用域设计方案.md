# 多形态用例生成与项目作用域设计方案

> 状态：**设计方案（本期仅文档，不落地业务代码）**。
> 范围：需求一 1.3「单项目多用例类型」与需求一 1.2 后续「APP 全链路生成管线」的落地蓝图。
> 前置：本期已落地代码——路由骨架（`case_kind` 扩 `app`、`_resolve_kind` 优先级、`app` 命中即抛 `SkillNotAvailable`、编排层转反问澄清）与会话增强（回答时间/批量删除/作用域过滤器，方案 A）。本方案在其上延伸，**不改动已发布的路由与落库红线契约**。

## 0. 现状基线（单一真源盘点）

设计与现状对齐，先固化「已经是什么」，避免设计与实现脱节。

### 0.1 项目模型：一项目 = 一类型 = 一文件
`backend/shared/project_store.py`：
- 注册表 `data/projects.json`，每项含 `id / name / desc / file / kind / builtin / created_at / updated_at`。
- `kind ∈ {api, ui, app}`（`KIND_API/KIND_UI/KIND_APP`），**单选**。
- 扩展名由 kind 决定并互斥：`api → .xlsx`、`ui → .json`、`app → .apjson`；新建落在 `data/cases/<pid><ext>`。
- 计数与读写按扩展名分流：`.apjson → app_case_store`、`.json → ui_case_store`、其余 → `excel_loader`（`_count_cases`）。
- `file` 路径创建后不可变（`update` 仅放行 `name/desc`），保证引用稳定、重命名安全。
- 默认项目 `default` 原地指向存量 `data/api_cases.xlsx`（`builtin=True`，不可删）。

### 0.2 三条用例存储链（口径单一真源）
| 类型 | 载体 | 校验权威 | 原子写 |
| --- | --- | --- | --- |
| 接口 api | Excel | `core/excel_loader` | 平台侧 |
| Web ui | 一项目一 JSON | `backend/ui/ui_case_store.validate_case` | `_LOCK + tmp + os.replace` |
| APP app | 一项目一 `.apjson` | `backend/app/app_case_store.validate_case` | `_LOCK + tmp + os.replace`（已具脚手架/校验，执行驱动 Appium 未接入） |

`app_case_store` 与 `ui_case_store` **同构**：`AppCaseError.kind ∈ invalid/not_found/conflict/locked`，动作元数据 `ACTIONS`（`launch/tap/long_press/input/swipe/key_press/assert_visible/assert_text/screenshot/wait`，各标 `locator/value` 需求），平台 `android/ios`，定位器前缀方言 `id=/xpath=/text=/accessibility_id=/class=/uiautomator=`。

### 0.3 落库闸门：接口与 UI 已对称，APP 缺位
- `backend/agent_bridge/case_gate.py`（接口）、`ui_case_gate.py`（UI）：同构 `preview`（逐条权威校验不落盘）+ `commit`（整批全合法才一次原子写；编号冲突 `_bump_id` 自动让号并回带 `renamed`；任一非法整批拒绝）。
- `resolve_ui_target`：项目必须存在且 `kind=ui`、显式 `file` 必须 `.json`——**防跨类型灌库**。
- **APP 无 `app_case_gate.py`**，平台无 `/api/agent/app-cases/{preview,commit}`。

### 0.4 Agent 侧路由（本期已落地）
- `agent/schemas.py`：`GenerationIn/ChatIn.case_kind ∈ Literal["auto","api","ui","app"]`。
- `agent/chat/intent.py`：`detect_kind` → `Intent.extras["kind_hint"]`（app>ui>api 关键词优先）。
- `agent/skills/case_generate.py` `_resolve_kind`：优先级 **显式 > kind_hint > 项目元数据(`project.read` kind) > api 缺省**；`run` 中 `kind=="app"` → `raise SkillNotAvailable`（**不静默转 api**）。
- `agent/chat/orchestrator.py` `_run_generate`：捕获 `SkillNotAvailable` → 发 `ask` 事件让用户改选接口/Web；`_resolve_scope`（方案 A）解析落库目标项目。
- `adapters/interfaceauto/adapter.py` `CAPABILITIES`：已有 `project.read`、`ui_case.{read,preview,write}`；**无 `app_case.*`**。
- `backend/agent_bridge/corpus.py`：`EXPORTABLE_DOMAINS=("contract","case","ui_case")`、`ALL_DOMAINS` 另含 `execution/business/convention`；**无 `app_case` 域**。
- `prompts/`：`case_generate.py`(P) + `ui_case_generate.py`(PU)；**无 `app_case_generate`**。

> 结论：APP 从「存储 + 校验」到「AI 生成」的距离，只剩 **闸门 + 语料域 + 适配能力 + prompt + skill 分支 + 前端草稿渲染** 六段装配，且 UI 轨已把每一段的范式跑通，APP 可逐段镜像。

## 1. 单项目多用例类型（1.3）

### 1.1 目标与约束
让一个被测系统同时挂接口/Web/APP 三类用例，且：
- **保持「一类型 = 一文件」原子性**（不因合并文件而破坏各 store 的独立锁与校验口径）；
- 存量单类型项目**零迁移**即可继续工作（向后兼容红线）；
- 落库闸门按类型分流，跨类型灌库仍被拒。

### 1.2 数据模型（推荐：`files` 映射，保留 `file` 兼容位）
现状 `file: str` + `kind: str`。改为**类型→文件**的映射，`kind` 语义降级为「主类型/缺省轨」：

```jsonc
// data/projects.json 条目（演进后）
{
  "id": "proj_xxx",
  "name": "统一相册",
  "desc": "...",
  "kind": "api",                     // 兼容位：主类型（老消费方读它）
  "file": "data/cases/proj_xxx.xlsx", // 兼容位：等价于 files[kind]
  "files": {                          // 新增：一类型一文件；缺键=该类未启用
    "api": "data/cases/proj_xxx.xlsx",
    "ui":  "data/cases/proj_xxx.json",
    "app": "data/cases/proj_xxx.apjson"
  },
  "case_types": ["api", "ui", "app"], // 前端 Tab 渲染顺序的显式声明（可选，缺省由 files 键序推导）
  "builtin": false,
  "created_at": "...", "updated_at": "..."
}
```

裁决要点：
- **读路径兼容**：老代码读 `entry["file"]/entry["kind"]` 不变；新代码优先读 `files[type]`，无 `files` 时回退 `{kind: file}`（`_normalize_files(entry)` 辅助）。
- **写路径按类型定位**：`resolve_target(project_id, case_type)` → `files[case_type]`；缺该键则「该项目未启用此类型」（区别于「文件不存在」——启用但为空由对应 store 首次写创建）。
- **原子性不破**：仍是每类型独立文件、独立 store 锁；`files` 只是注册表里的多指针。
- **不变式**：`set(files.keys()) == set(case_types)`，`files[kind] == file`；`create`/`add_type`/迁移脚本统一维护。

### 1.3 目录结构
延续 `data/cases/<pid>.<ext>`，三扩展名并存互不冲突：
```
data/cases/
  proj_xxx.api.xlsx     // 或存量沿用 <pid>.xlsx；见 1.6 迁移
  proj_xxx.ui.json
  proj_xxx.app.apjson
```
> 存量项目文件名为 `<pid>.<ext>`（无类型中缀）。是否统一改带中缀取决于迁移成本（见 1.6）；本方案**不强制改名**，以 `files` 映射记录实际路径为准，规避重命名断开引用。

### 1.4 注册表读写接口演进
`project_store`：
- `create(name, desc, kind)` 保持不变（建单类型项目）；新增 **`enable_type(project_id, case_type)`**：按 kind 脚手架对应文件、写入 `files[case_type]` 与 `case_types`，锁内原子更新注册表（先脚手架后登记，失败不留孤儿，复用现有 `create` 的「先文件后登记」次序）。
- `get/list_projects` 回带 `files`/`case_types`（浅拷贝，不动引用）。
- `delete` 扩展：删项目时遍历 `files` 全部值逐个清理（现状只删单 `file`），仍限定 `data/cases/` 下防路径穿越。
- 新增校验：`_validate_files(entry)`——键合法、扩展名与类型匹配（api→xlsx、ui→json、app→apjson）、`file==files[kind]`。

`backend` 路由：`/api/projects` 列表/详情回带 `files`；新增 `POST /api/projects/{pid}/types`（启用某类型，body `{case_type}`）；`PATCH` 不变。

### 1.5 生成流程（case_kind 选轨 + 按类型解析目标文件）
Agent 侧改动最小，因本期路由骨架已按 `kind` 分流：
1. `_resolve_kind` 得出 `kind`（显式/kind_hint/项目元数据）。**多类型下项目元数据不再唯一决定 kind**——`project.read` 回包应带 `case_types`，`_resolve_kind` 的「项目元数据」分支调整为：项目仅一类→用该类；多类且无显式/kind_hint→返回 `auto` 交编排层按对话意图或反问（呼应作用域反问精神，不盲选主类型）。
2. `run(kind)` 选轨（api/ui/app 各自的 `_run_*`）。
3. 落库 preview/commit 传 `project_id + case_type(=kind)`，平台 `resolve_*_target` 据 `files[kind]` 定位，替代现状「按项目唯一 `file`」。
4. 跨类型灌库防护升级：`resolve_ui_target/app` 由「kind 必须=ui/app」改为「`case_type` 必须已在该项目 `case_types` 且 `files[case_type]` 存在或可脚手架」，扩展名再校验双保险。

### 1.6 迁移与兼容
- **零迁移启动**：读路径兼容位（`file`/`kind`）保证存量单类型项目照旧；`list/get` 对无 `files` 的条目即时派生 `{kind: file}`。
- **渐进增强**：用户在前端「添加类型」→ 触发 `enable_type` 脚手架新文件，写回 `files`，此后该项目多类型并存。
- **存量文件名不改**：迁移不做批量重命名（避免 `file` 变更断引用）；仅新启用类型文件用带类型中缀（可选，非必须）。
- **注册表一次性升级（可选幂等脚本）**：`tools/migrate_project_files.py` 遍历把 `file→files[kind]` 显式化；纯补字段，不改文件路径，可重复执行。

### 1.7 前端交互（项目内类型 Tab）
- 项目详情/用例页顶部 **类型 Tab（接口 / Web / APP）**，按 `case_types` 渲染；无该类型文件时 Tab 显「未启用 · 点击启用」→ 调 `enable_type`。
- 切 Tab = 切 `case_type`，列表/编辑/执行各按类型走对应 store 端点（`/api/cases`、`/api/ui-cases`、`/api/app-cases`）。
- 项目选择器（AI 助手顶栏）在「不限」过滤器下不变；选中多类型项目时，`case_kind` 依对话 `kind_hint` 或让用户在反问里定（呼应 1.5(1)）。

### 1.8 落库闸门按类型分流
`case_gate/ui_case_gate/app_case_gate` 三者 `resolve_*_target` 统一签名 `resolve_target(body, case_type)`，`body` 带 `project_id + (file | case_type)`；闸门各按 `files[case_type]` 取路径，其余 `preview/commit` 逻辑不变（各类型权威校验口径仍单一真源）。

## 2. APP 全链路生成管线

目标：仿 UI 轨把 APP 从「占位反问」升级为「可生成—可校验—可人工确认落库」的完整链路。**存储与校验已就位（`app_case_store`）**，本节补齐其余六段。落库红线不变：降级 / 非权威 / 未过闸任中其一绝不自动落库。

### 2.1 平台闸门 `backend/agent_bridge/app_case_gate.py`（镜像 ui_case_gate）
- `resolve_app_target(body)`：项目须存在且启用 app 类型（`files["app"]`），显式 `file` 须 `.apjson`；默认文件可不存在（新项目首次写创建）。
- `preview(cases, project_id, file)`：逐条 `app_case_store.validate_case`，回 `{platform, file, checked, passed, failed, items, summary}`；编号已存在提示「落库时自动递增改名」。
- `commit(cases, project_id, file, meta)`：整批先校验，全合法才 `_append_all` 一次原子写；`AppCaseError.kind → HTTP` 映射 `{invalid:400, not_found:404, conflict:409, locked:409}`；冲突 `_bump_id` 让号并回带 `renamed`；任一非法整批拒绝。
- `_append_all` 复用 `app_case_store._LOCK + _read/_write`。
- 路由注册：`POST /api/agent/app-cases/preview` 与 `/commit`，权限同 UI（`case:write`，服务账号 `agent_svc`）。

### 2.2 语料域 `app_case`（corpus.py）
- `EXPORTABLE_DOMAINS += ("app_case",)`；`ALL_DOMAINS` 已含扩展位。
- 新增 `app_case_records(base_url, since, project_id, file)`：镜像 `ui_case_records`，遍历启用 app 的项目读 `.apjson`，一步→中文动作句（动作名取自 `app_case_store.ACTIONS` 单一口径，`launch/tap/...` 与其 `desc`），`kb_id=_kb_id("app_case", pid|rel, case_id)`、`domain="app_case"`、`platform=PLATFORM("interface-auto")`。
- `export_domain` 增 `if domain == "app_case": return app_case_records(...)`。
- 语料作用：给模型「本项目/平台已有 APP 用例长什么样」的风格样板与既有编号，减少编号冲突与动作臆造。

### 2.3 适配能力 `app_case.*`（adapter CAPABILITIES）
`adapters/interfaceauto/adapter.py` 增三条，路径对应 2.1：
```python
"app_case.read":    {path: "/api/app-cases",            method: "GET"}
"app_case.preview": {path: "/api/agent/app-cases/preview", method: "POST"}
"app_case.write":   {path: "/api/agent/app-cases/commit",  method: "POST"}
```
`invoke` 分发已按 `method` 通吃（POST 进 body、GET 拼 path），无需改分发逻辑；`manifest.capabilities` 白名单放开这三项即可。

### 2.4 Prompt `prompts/app_case_generate.py`（AP，镜像 ui_case_generate）
- `system_prompt()`：自述「APP 移动端用例生成器」，输出**严格 JSON**（`APP_CASE_OUTPUT_SCHEMA`），字段对齐 `app_case_store.validate_case` 产出形状：`case_id/module/name/desc/priority/run/platform(android|ios)/app(包名或BundleID/deeplink)/steps[]/extract[]/pre_scripts/post_scripts`。
- **动作白名单单一口径**：`APP_ACTION_META = {action: (need_locator, need_value)}` 与 `app_case_store.ACTIONS` 严格一致（launch/tap/long_press/input/swipe/key_press/assert_visible/assert_text/screenshot/wait）；`ACTION_ALIASES` 收口语别名（「点一下→tap」「左滑→swipe+value=left」「返回键→key_press+value=back」）。
- `VALID_PRIORITIES = {P0..P5}`、`VALID_PLATFORMS = {android, ios}`；定位器方言说明（`id=/xpath=/text=/accessibility_id=`，裸值按 `accessibility_id`）。
- `build_user_prompt(mode, target, intent, existing, reference, var_pool, count, ...)`：注入既有 APP 用例样板 + 语料 reference + 编号避让提示 + 变量池；要求「至少一个断言步（`assert_*`）、`launch` 起手、`{{var}}` 仅用池内变量」。
- `APP_CASE_OUTPUT_SCHEMA`：JSON Schema 强约束，供 `provider.chat(json_schema=...)`。

### 2.5 Skill 分支 `case_generate.py`（把 app 从「抛未装配」升级为「走轨道」）
- 移除 `run` 中 `kind=="app" → raise SkillNotAvailable` 的占位；改为 `if kind == "app": return self._run_app(...)`。
- 新增 `_run_app`，**完全镜像 `_run_ui`**：
  - `_app_context(adapter, project_id)`：`project.read` 校验启用 app 类型 + 取 `files["app"]` → `app_case.read` 拉存量（风格/编号去重/变量池三用）；读不到不阻断，平台侧兜底。
  - `_assemble_app(...)`：`retriever.assemble(query, ..., required=(), optional=("app_case","convention"), ...)`（APP 无契约硬依赖）。
  - `_generate_app(...)`：`provider.chat(messages, json_schema=AP.APP_CASE_OUTPUT_SCHEMA)` + 一次 repair 回炉（与 `_generate_ui` 同款循环）。
  - 闸门 `gate_app_case(case, ctx, var_pool, taken_ids)`：结构/动作白名单(`AP.APP_ACTION_META`)/`{{var}}` 子集/编号去重/`citations` 强制——口径对齐 `gate_ui_case`，权威裁决仍在平台。
  - `_authoritative_check(..., kind="app")` 扩：`cap = "app_case.preview"`、`write_cap = "app_case.write"`。
  - 产出 `data.case_kind="app"`，`diffs` 用 `_APP_DIFF_FIELDS`。
- `_resolve_kind` 已认 `app`（本期），无需改；`ui_hint` 旁可加 `app_hint` 或直接依赖 `kind_hint`。
- 编排层 `_run_generate` 的 `SkillNotAvailable→ask` 分支**保留为防御**（若将来某平台未装 app 轨仍优雅降级），但正常路径不再触发。

### 2.6 前端 APP 草稿渲染
- Agent 预览面板按 `case_kind` 选渲染器：APP 草稿用移动端步骤条（动作中文名 + 定位器/取值 + 平台 android/ios + 被测 app），逐条校验报告与 `registered` 事件沿用现有 SSE 契约（`case_ready/validation/diff/citation`）。
- 项目用例页「APP」Tab（呼应 1.7）列表/编辑器对接 `/api/app-cases` CRUD + `app_case_store.meta`（动作下拉/平台候选）。
- 执行侧：Appium 驱动**尚未接入**，APP Tab 先支持「编辑/校验/存储」，执行按钮置灰或标注「规划中」，与 README 的「平台已具存储与执行、AI 生成为规划中」表述校准（后续接入执行时更新该措辞）。

### 2.7 测试计划（落地本期文档之后的实现期）
- **平台 `unit_tests/`**：`test_app_case_gate.py`（preview 逐条权威 + commit 整批拒绝/让号 `renamed`/跨类型灌库被拒）；`test_corpus_app_case.py`（`app_case` 域导出、`kb_id` 稳定、动作中文句）；`/api/agent/app-cases/*` 端点权限与状态码。
- **Agent `tests/`**：`_resolve_kind` 命中 app 走 `_run_app`（不再抛 `SkillNotAvailable`，改用桩 adapter `app_case.read/preview/write`）；`gate_app_case` 动作白名单/变量/编号/引用；prompt JSON Schema 解析 + repair 回炉；`case_kind="app"` 产出与 diff；`app` 降级红线（degraded/authoritative=False 不落库）。
- **evals**：给一段「登录安卓 App」对话，断言产出含 `launch` 起手 + 至少一 `assert_*` + 无未定义变量。
- **回归**：双 venv `pytest`（平台 `unit_tests/` + `qa-agent tests/`）全绿；`npm run build` 通过。

### 2.8 落地顺序（建议切片）
1. 闸门 `app_case_gate` + 平台端点 + 单测（纯平台，先具备「能校验能落库」）。
2. corpus `app_case` 域 + adapter `app_case.*`（打通语料与能力面）。
3. prompt `app_case_generate` + skill `_run_app` + gate + Agent 测试（打通生成）。
4. 前端 APP 草稿渲染 + 项目 APP Tab（打通人机闭环）。
5. 与「单项目多类型」合流：`resolve_app_target` 读 `files["app"]`。

> 切片 1–2 独立可发（不依赖多类型改造）；3 起与路由骨架自然衔接（`SkillNotAvailable` 占位替换即生效）。

## 3. 兼容与红线汇总

- **落库红线不变**：降级 / 非权威（平台离线，`authoritative=False`）/ 未过确定性闸门任中其一，绝不自动 commit；APP 严格继承。
- **契约 id 稳定**：`platform="interface-auto"` 不随仓库改名变动（adapter/corpus `PLATFORM`/sessions/前端请求体）；APP 各 `kb_id`、能力名沿用同平台维度。
- **跨类型灌库防护**：三 `resolve_*_target` 各校验目标类型与载体扩展名，双向兜底。
